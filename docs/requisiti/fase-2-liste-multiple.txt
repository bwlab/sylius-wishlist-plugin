Stage 2 — Multiple Wishlists
Task Type: Story​
Title: Implement Multiple Named Wishlists


Description
As a customer, I want to create and manage multiple named wishlists so that I can organize
my favorite products for different purposes, such as birthdays, Christmas, or personal
shopping plans.

Extend the existing Basic Wishlist functionality to support multiple independent wishlists per
customer.

Customers should be able to create, view, rename, and delete wishlists, select which wishlist
to add a product to, and manage products within individual lists.

For example, a customer might create the following wishlists:

   ●​ My Favorites — products they personally like.
   ●​ Birthday — products they would like to receive as gifts.
   ●​ Christmas — products they are considering for the holidays.

Each wishlist should have its own name and collection of products.

All existing functionality from Stage 1 must remain available.

User Acceptance Criteria
  ●​     Customers can create multiple named wishlists.
  ●​     Each wishlist has a name and an independent collection of products.
  ●​     Customers can view all their wishlists in one place.
  ●​     Customers can select a wishlist and view its products.
  ●​     Customers can choose a destination wishlist when adding products from PDP or
         PLP.
  ●​     The same product can belong to multiple wishlists.
  ●​     Duplicate product entries within the same wishlist are prevented.
  ●​     Customers can rename existing wishlists without losing their contents.
  ●​     Customers can delete individual wishlists without affecting other wishlists or
         catalogue products.
  ●​     Deleting a wishlist requires confirmation.
  ●​     Customers can remove products from individual wishlists without affecting other lists.
  ●​     Customers can move products between wishlists.
  ●​     Wishlist names cannot be empty or consist only of whitespace.
  ●​     Authenticated customers' named wishlists persist between login sessions.
  ●​     Guests can manage multiple wishlists, which survive page refreshes within the same
         browser.
  ●​     Customers cannot access or modify another customer's private wishlists.
  ●​     Existing single-product and multi-product Add to Cart functionality works within each
         wishlist.
  ●​     All existing Stage 1 functionality remains operational.
   ●​ The complete functionality can be demonstrated through the storefront UI.


Technical Details
The implementation must remain compatible with the existing Stage 1 solution.

Participants are free to choose the architecture, data model, persistence strategy, and user
interface.

Data model

Consider separating the wishlist itself from its product entries.

A single customer or guest may own multiple wishlists.

A product may belong to multiple wishlists, but should occur only once within each individual
wishlist.

Guest wishlist persistence

The guest identification mechanism introduced in Stage 1 can be reused.

Cookies, browser storage, or server-side guest identifiers are acceptable approaches.

Guest wishlists should remain isolated from other visitors.

Authenticated customers

Named wishlists should be associated with the authenticated customer and stored
persistently.

The implementation should respect existing platform authentication and authorization
mechanisms.

Existing MVP compatibility

If Stage 1 introduced a single unnamed wishlist, participants may:

   ●​ Convert it into a default wishlist, such as "My Favorites".
   ●​ Keep it as the default wishlist while supporting additional named lists.

Existing saved products should not be lost when extending the functionality.

Product operations

Product addition, removal, and cart integration should reuse the existing functionality
wherever possible.

Moving a product between wishlists may be implemented as a dedicated operation or as a
combination of adding to the target list and removing from the source list.
Frontend implementation

The interface may use dropdowns, modals, separate pages, or traditional HTML forms.

AJAX interactions are optional.

Testing

Automated tests are welcome but not mandatory.

The implementation will be evaluated through a live demonstration against the acceptance
criteria.
